
1. “请不使用‘一致性’、‘可用性’或‘分区’这几个词，向我解释 CAP 定理。”
	
	要么选择**锁死系统，拒绝任何读写操作**（确保数据绝对没有误差，但得罪用户）； 
	要么选择**继续咬牙接客，给出答复**（安抚了用户，但由于无法同步，只能提供可能已经过期或冲突的信息）。
	绝无第三条路可走。
	
2. “你的微服务需要一个分布式事务来保持数据同步。你会如何实现它？”
	
	1. **反思拆分：** 这两个服务是不是耦合太紧了？能合在一起用本地事务解决吗？ 
	2. **挑战业务：** 我们真的需要“此时此刻绝对一致”吗？能不能改成“先记账，后对账”，只要最后钱没少就行？
	
3. “告诉我一次你故意选择‘无聊’、过时的技术，而不是现代、热门技术的经历。为什么？”
	
	在实际商业环境中，我曾接手一个需要处理每天约 50 万条用户行为日志的模块。 
	* **菜鸟团队的提案（追逐时髦）：** 强烈要求引入 Apache Kafka 作为消息队列削峰，用 Flink 进行流处理，最后落库到 ElasticSearch 集群。理由非常耳熟：“大厂都是这么搞大数据的。” 
	* **专家强制落地的方案（主动无聊）：** 砍掉所有花哨的中间件 。直接用一个单机版的 **PostgreSQL** 数据库，建好合适的索引，配合一个几十行的 Python 脚本和 Linux 最古老的 **Cron（定时任务）**，每隔一小时批量把日志插进库里。
	
	因为：
	1.  一个公司的精力和资源是极其有限的，应该把宝贵的“创新代币”花在**核心业务逻辑**。
	2.  招一个精通传统关系型数据库（如 MySQL/PG）的工程师非常容易。但想找一个能在生产环境下排查 K8s + Service Mesh 诡异网络丢包问题的顶级专家极难。
	3.  “无聊”的技术经历了二三十年的残酷考验。它的每一个 Bug、每一个性能瓶颈，在网上都有现成的成熟解决方案。
	 
4. “如果我要求你明天把我们的关系型数据库换成 NoSQL 数据库，系统里最先崩溃的是什么？”
	
	你的应用服务器会因为内存溢出最先宕机，紧接着你的业务逻辑会因为‘数据孤儿’彻底错乱。
	
	* **关系型数据库** 承担了大量的脏活累活：保证格式统一（Schema）、保证关系不乱（外键）、负责复杂计算（JOIN）、保证生死与共（ACID 事务）。它牺牲了一点速度，保全了应用代码的简单。
	* **NoSQL** 跑得极快、能无限扩展，是因为它把所有的包袱都扔掉了。
	
5. “在‘黑五’期间，如果支付网关宕机，你的系统将如何优雅降级 ？”
	1. 立刻熔断 
	2. 转换业务状态
	3. 将“同步”降级为“异步” 
	4. 后台重试补偿 
	5. 人工接入核对剩余账单
6. “实现 API 网关真正隐藏的代价是什么？”
	API 网关解决的是“外部混乱”的问题，但代价是极大地加剧了“内部管理的复杂度”
	
	1. 组织协同的“肠梗阻”
	2. 业务逻辑的致命泄露
	3. 无法豁免的“毫秒税”
	
7. “你如何对一个面向公众的 API 进行版本控制，而不强迫现有客户端立即升级？”
	
	我会通过 URL 或 Header 路由实现多版本并行，然后开启漫长的‘日落流程’。**API 升级的成本，必须由我们服务端架构来承担和消化，绝不能强行转嫁给信任我们的客户。
	
	1. 并行服务，新老划断
		面馆引入了扫码点餐（v2），但依然保留人工点餐台（v1）。在技术上，专家会在 API 网关层通过 URL 路径（如 `/v1/orders` 和 `/v2/orders`）或 HTTP Header 请求头（如 `Accept-Version: v2`），将流量精准分发到两套并行运行的控制器代码上。老客户依然可以吃面，新客户享受新功能。**
	2. 非破坏性扩展优先
		如果是加个“小菜”，千万不要发 v2。专家恪守“伯斯塔尔法则”：发送时要保守，接收时要宽容。 在 v1 接口里直接增加一个可选的 `discount_code` 字段。旧客户端不认识这个字段，会直接忽略它（宽容处理），系统绝不会报错。**
	3. 极其漫长的“优雅日落”
		当你真的必须淘汰 v1 削减维护成本时，绝对不能搞偷袭。
		 1. 警告阶段： 在 v1 的 API 响应头中加入 “贬值：真” 和 `Sunset: 2026-12-31`。这样对方工程师在查日志时就会看到警告。
		 2. 通知阶段： 给依然在使用 v1 的大客户发送倒计时邮件，提供详尽的迁移文档。 
		 3. 演习阶段（Brownout 测试）： 在深夜，故意制造几次极其短暂的 v1 接口“人为限流”或返回特定错误码。这就像拔一下对方的网线立刻插上，逼迫那些“装睡”的客户意识到痛点，主动安排研发资源升级到 v2。
	4. 斩断旧轨
		直到监控系统显示 v1 的流量彻底归零，并且日落期满，才会彻底下线旧代码。
	
8. “我们遇到了缓存雪崩/击穿 ，导致主数据库瘫痪。向我演示你的缓解策略。”
	1. 熔断与限流
	2. 互斥锁
	3. 缓存随机过期时间
	4. 逻辑时间过期与异步刷新
9. “你需要从系统中删除一个核心的老旧遗留模块。你的架构如何支持这种‘反向操作’？”
	
	承认技术栈迟早会过时，并在架构之初就做好准备。
	
	1. 引入防腐层 
		在不动老模块一行代码的前提下，在其前方放置一个 API 网关或代理层。所有其他模块必须通过这个代理层才能访问老模块。这确立了出入的唯一关卡。
	2. 增量重写
		在老模块旁边，开发全新的模块。此时，代理层开始进行流量路由：将 90% 的旧功能请求依然发给老树，但将 10% 的特定请求（比如某个新加入的白名单用户群体）悄悄引流到新藤蔓上。
	3. 影子流量测试
		为了确保新模块的逻辑 100% 正确，专家会开启“影子模式”。代理层把真实的业务流量同时发送给老模块和新模块。但是，系统只返回老模块的结果给用户。后台有一个异步进程，专门比对新老模块的计算结果差异。一旦发现不一致，立刻修复新代码，而用户毫无察觉。
	4. 日落与下线 
		当新模块经过几周的影子测试，证明完全稳定后，代理层将路由权重调至 100% 指向新模块。 此时，那棵老树（遗留模块）虽然还在服务器上，但已经没有任何流量进入（被饿死了）。监控系统确认它连续 30 天 CPU 负载为 0。直到这时，专家才按下删除键，安全地回收服务器资源。
10. “你会用什么具体的指标向 CEO 证明，你的架构重构是成功的？”
	
	重构后，在风险、效率和投资回报率上得到了改善。
	
	1. 交付前置时间缩短（敏捷性） 
		专家的话术： “老板，以前市场部想上一个满减活动，因为系统严重耦合，开发加测试需要 3 周。重构解耦后，上个月同样的活动，我们只用了 3 天就推向了市场。我们帮公司抢占了 18 天的市场先机。” 
	2. 平均恢复时间与可用性（韧性与风控）
		专家的话术： “去年双十一，系统崩溃了 2 小时，彻底排查修好花了大半天，按每小时 50 万的营业额算，我们直接损失了 100 多万。这次重构引入了自动熔断和隔离机制。上周其实支付网关也挂了一次，但因为系统做了优雅降级，前端用户根本没感觉，系统自动恢复只用了 5 分钟（MTTR 降低）。这次重构帮公司保住了今年双十一的底盘。” 
	3. 单笔交易的云算力成本（极致效率） 
		专家的话术： “以前我们的系统无论有没有用户，几百台高配服务器都要一直开着。重构为弹性伸缩架构后，在凌晨没有订单时，服务器会自动缩减。摊销下来，我们每促成一笔 100 元的订单，IT 服务器成本从过去的 5 毛钱，硬生生降到了 1 毛钱。按千万级日单量计算，这每年能为公司净省出几百万的纯利润。”
